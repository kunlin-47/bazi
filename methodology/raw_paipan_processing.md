# 原始排盘软件输出 → AI 静态分析文件 · 处理方法论

> **本文件是本仓库相对 [`kunlin-47/xty`](https://github.com/kunlin-47/xty) 等同类项目的核心增量。**
>
> 同类项目通常默认从"已经准备好的 `static_chart.json`"开始工作；本仓库多了一步前置流程：从专业排盘软件的原始文本输出（如《南方排八字专业程序》），经过 AI 化处理与剔除，转化为机制透明、AI 易读的静态分析文件。
>
> 这个步骤的核心问题：**专业排盘软件的输出包含大量"黑箱"内容**——口诀直断、机制不透明的神煞、与命局结构无关的位理建议、按生肖机械匹配的婚配清单等。如果直接把原始输出喂给 AI 做后续推演，AI 会被这些黑箱信息污染。
>
> 本文档定义"过滤 + 重构"的方法论。

## 一、问题陈述

### 1.1 排盘软件能做什么 / 不能做什么

| 软件擅长 | 软件不擅长 |
|---------|-----------|
| 八字四柱排盘（年月日时干支） | 用神判断（机制不透明的"综合得分"） |
| 大运序列推演（按节气精确计算） | 格局判定（按口诀套用，缺乏机制说明） |
| 藏干、十神、纳音、神煞速查 | 婚配、子嗣、健康、风水类断语（黑箱口诀） |
| 起运时间计算 | 解释"为什么得出这个结论" |

### 1.2 软件输出中常见的"黑箱"类型

以《南方排八字专业程序》为例，原始文本输出中可识别出至少 8 类机制不透明的内容：

1. **综合旺衰得分**（如 "-42 八字过弱"）：算法不公开，仅作旁证不可作主判
2. **婚配建议**（如"宜配属相 X"、"推荐结婚时间"）：按年支生肖机械匹配，跨命局通用
3. **头胎性别口诀**（如"头胎易生女儿"）：机制不透明
4. **马倒禄斜虚岁列表**（如"X 岁马倒禄斜"）：实际机制为**岁运并临**（大运柱 = 流年柱），但软件用了不透明口诀名
5. **位理类信息**（楼层、桃花位、文昌位、避忌方位、命卦、游年卦）：与子平不同源
6. **口诀类神煞**（红鸾、太极、绞煞、孤辰、寡宿、丧门、吊客、披麻、白虎、卷舌、天医等）：算法不透明
7. **健康直断**（"心脏血液有毛病"、"小心关节炎"等）：超出推命可推范围，应交医生
8. **个性化吉凶口诀**：缺乏推演链，无法验证

### 1.3 为什么必须做这一步处理

如果直接把原始输出喂给下游 AI：

- AI 会把"-42 八字过弱"当作权威判断，覆盖更准确的扶抑分析
- AI 会引用"宜配属相虎"这种与命局结构无关的建议，污染婚姻分析
- AI 会列出"X 岁马倒禄斜"作为预警，但说不出机制，命主问"为什么"时无言以对
- AI 会混入"红鸾入命"这种口诀，无法验证也无法推演

**结论**：必须建立一道过滤层，把黑箱内容剔除并标注理由，把可保留的内容机制化重写。

## 二、剔除原则

### 2.1 必剔除（无例外）

凡符合以下任一条件，**必须剔除**且不留作旁证：

| 类别 | 判别标准 | 处理 |
|------|---------|------|
| 健康直断 | 给出具体病灶（如"心脏病"、"高血压"）但无机制链路 | 完全剔除，写入 `_meta.scope.excluded` |
| 婚配年份口诀 | 按生肖机械匹配（"宜配属猪"、"X 年宜婚"） | 完全剔除 |
| 位理建议 | 楼层、桃花位、避忌方位、命卦 | 完全剔除（位理范畴，与子平不同源） |
| 头胎性别口诀 | "头胎易生 X" | 完全剔除 |

### 2.2 剔除但保留作旁证

凡符合以下条件，**剔除主结论但保留作旁证标记**——记录到 `_meta.stance_on_software_outputs` 字段，下游 AI 可知道软件给过这个结论但本分析不采纳：

| 类别 | 判别标准 | 处理 |
|------|---------|------|
| 综合旺衰得分 | 软件给出 "-X / +X" 数字与"X弱 / X强"定性 | 仅保留得分数字 + "黑箱算法仅作参考"标注，不取极端定性 |
| 口诀类年龄列表 | "X 岁 X 关 / X 岁马倒禄斜" 等 | 剔除原口诀名，但若有实际机制（如岁运并临）则改名重新收录 |
| 口诀类神煞 | 红鸾 / 天喜 / 太极 / 绞煞 / 孤辰 / 寡宿 / 丧门 / 吊客 / 披麻 / 白虎 / 卷舌 / 天医 等 | 剔除，标注"机制不透明" |
| 流派争议性结论 | 不同流派结论冲突 | 标注"流派分歧"，选定主线（本仓库主线为子平派 + 《子平真诠》/《滴天髓》）|

### 2.3 剔除时必须显式说明

每一条被剔除的内容**都要在静态分析文件的 `_meta.scope.excluded` 或 `_meta.stance_on_software_outputs` 中显式列出**——不允许"默默不收录"。原因：

- 让下游 AI 知道这件事被评估过，不会再次主动引入
- 让命主能查到"为什么软件给了 X 但分析里没有"
- 让 methodology 修订时有迹可循

## 三、保留与重构原则

### 3.1 必保留（机制清晰）

| 类别 | 判别标准 | 处理 |
|------|---------|------|
| 八字四柱 | 年月日时干支八字 | 直接采用，作为静态分析的核心输入 |
| 大运序列 | 起运年龄、每步干支、起止年份 | 直接采用，对照节气日 |
| 藏干 | 每支本气 / 中气 / 余气 | 直接采用（对照 `lookup_tables.md` §二） |
| 纳音 | 干支纳音 | 仅作辅助标记，不参与主推演 |
| 旬空 | 日柱旬空两支 | 必保留，作"印根折损 / 禄神被空"等结构判断的核心证据 |
| 月令分日用事 | 节气进入第几日 | 保留并标注当下用事的主气强度 |

### 3.2 重构后保留（剔除原命名 + 重新机制化）

| 原始命名 | 实际机制 | 重构命名与处理 |
|---------|---------|---------------|
| 马倒禄斜（X 岁） | 岁运并临（大运柱 = 流年柱） | 改记为"岁运并临年"，写入 `key_years_for_dynamic_analysis` |
| 童子煞 | 出生月份 + 时辰组合 | 暂不收录（机制争议） |
| 八字过弱 / 偏弱 | 软件综合旺衰打分 | 改为基于"令、地、势 + 调候"的扶抑判断，软件得分仅作旁证 |

### 3.3 神煞保留原则（机制清晰）

参照 `lookup_tables.md` §十三的标准——**仅保留**：

- 禄神（日干临官位）
- 羊刃（阳干劫财在帝旺地）
- 将星（三合局之中字 / 旺位）
- 华盖（三合局之库 / 末字）
- 驿马（三合局之冲位）
- 文昌（口诀但规则稳定）
- 天乙贵人（按日干起，每日干两支）
- 月德 / 天德（按月支三合局推）

每个保留的神煞**必须在静态分析文件中标注其推导机制**——不只是"命主有华盖"，要写明"寅午戌之华盖在戌（三合局之库位）→ 以日支戌起算 → 本造命中"。

### 3.4 男女命专属维度的机制化

排盘软件常用口诀直断婚姻、子女，本仓库要求**机制化处理**：

- 妻 / 夫星：以正财（男）/ 正官（女）为主，偏财 / 七杀为偏。原局有无明透、藏哪柱、是否得地、是否被冲被合——逐项写明
- 妻宫 / 夫宫：日支。藏干本气是什么？与月柱、时柱有什么互动（合 / 冲 / 害 / 刑）？
- 子女星：男命以官杀（甲乙）、女命以食伤（戊己于丙日主等）为主。原局是否得地、是否有根
- 子女宫：时柱。藏干结构？与日柱关系？
- **不收录**软件给出的"宜婚年份"、"子女数量"、"婚配属相"等机械匹配清单

## 四、静态分析文件的格式约定

### 4.1 文件命名与拆分

本仓库当前命主的静态分析文件采用**三文件拆分**：

```
bazi-static-analysis_1.json    # _meta + 基础信息 + 八字 + 十神 + 盘面几何 + 旺衰 + 不从原因
bazi-static-analysis_2.json    # 格局 + 空亡 + 触发钩子 + 地支动态 + 五行
bazi-static-analysis_3.json    # 性格 + 男/女命专属 + 神煞 + 大运 + 岁运并临 + 总结
```

拆分原因：单一文件超过 30KB 后 AI 加载与处理效率下降；按"基础 / 结构 / 演化"三层分文件读起来也更清晰。

### 4.2 必备字段

文件 1 必须包含 `_meta`，至少含以下子字段：

```json
{
  "_meta": {
    "purpose": "...",                          // 文件目的
    "pipeline": "...",                         // 整体处理链路
    "scope": {
      "included": [...],                       // 包含的内容
      "excluded": [...]                        // 显式剔除的内容
    },
    "shensha_filter_principle": "...",         // 神煞过滤原则
    "key_style": "...",                        // 字段命名风格说明
    "stance_on_software_outputs": {            // 对原排盘软件具体输出的态度
      "综合旺衰得分": "...",
      "推荐结婚时间": "...",
      "马倒禄斜虚岁列表": "...",
      "口诀类神煞": "...",
      "...": "..."
    },
    "core_judgments": [...]                    // 核心判断的一句话总结（便于下游 AI 快速定位）
  }
}
```

### 4.3 字段命名约定

- **字段名英文**：保证 JSON Schema 友好、利于程序化引用
- **内容值中文**：保留命理术语精度
- **机制标注内联**：每个判断附上"为什么"——例如不写 `"将星": true`，要写 `"将星": "巳酉丑三合局之将星在酉（三合局之旺位）→ 以年支巳起算 → 本造命中"`

### 4.4 空亡的双层结构

参照 [`basics.md`](./basics.md) §七的"年柱旬空 vs 日柱旬空"原则：

```json
{
  "empty_branches": {
    "primary_day_void": ["辰", "巳"],
    "primary_void_xun": "甲午旬（戊戌日属此旬，旬空辰巳）",
    "secondary_year_void": ["申", "酉"],
    "secondary_void_xun": "甲戌旬（辛巳年属此旬，旬空申酉）",
    "stance": "本分析以日柱旬空为主用..."
  }
}
```

### 4.5 待发与已成的地支动态

地支关系分两类：

- **已成**（原局四柱中已经发生的合冲刑害）：直接列出位置、机制、效应
- **待发**（须大运 / 流年触发的潜在关系）：列出触发条件、效应、对原局影响、权重

分类清晰可避免动态分析时混淆"原局已有"和"运程触发"。

### 4.6 触发钩子按吉凶分类

参照本仓库 `bazi-static-analysis_2.json` 的 `structure_activation_hooks`：

```json
{
  "structure_activation_hooks": {
    "favorable_activations": [...],      // 吉
    "unfavorable_activations": [...],    // 忌
    "neutral_dual_use": [...]            // 双刃
  }
}
```

下游动态分析 AI 看到一个运至时，能立刻索引到"这是吉触发还是忌触发"。

## 五、流程：从原始输出到静态分析文件

### 5.1 标准处理流程

```
1. 输入：原始排盘软件文本输出（如 南方排八字专业程序.txt）
       ↓
2. 信息提取：四柱、藏干、大运、纳音、空亡等结构性数据 → 直接保留
       ↓
3. 黑箱过滤：综合得分、婚配口诀、马倒禄斜、位理建议 → 标注剔除理由
       ↓
4. 神煞过滤：按 §3.3 原则保留机制清晰的，剔除口诀类
       ↓
5. 重构机制化：把"马倒禄斜" → "岁运并临"等改名重新收录
       ↓
6. 补充本仓库独有的字段：chart_topology、structure_activation_hooks、男/女命专属、
                       key_years_for_dynamic_analysis 等
       ↓
7. 三文件拆分：按"基础 / 结构 / 演化"三层组织
       ↓
8. 输出：bazi-static-analysis_{1,2,3}.json + 命主级 README
```

### 5.2 处理过程中的"诚实纪律"

- **不臆造数据**：若原始排盘软件没给出某项（如出生地真太阳时校正），静态文件不能假装有
- **剔除必显式说明理由**：在 `_meta.stance_on_software_outputs` 里写清楚为什么剔除
- **流派分歧时显式标注**：如"本仓库采用 X 派"
- **遇到与排盘软件结论矛盾时显式标注**：如"排盘软件给出 -42 偏弱，本分析判为偏弱有根"——不悄悄覆盖

### 5.3 prompt 化

把上述流程固化为可复用的 AI 提示词：[`prompts/static_extraction.md`](../prompts/static_extraction.md)。

未来如果给其他命主做静态分析，按该 prompt 跑即可。

## 六、维护与迭代

### 6.1 修订动机

只有以下三种动机才修订本文档：

1. **新发现一类黑箱输出**：从更多排盘软件输出中识别出新的不透明类别 → 加入剔除清单
2. **某条原则被实证修正**：原本标注"剔除"的条目实际有清晰机制 → 调整为保留
3. **格式约定调整**：静态分析文件的字段结构演进时同步更新

### 6.2 不修订的情况

- 命主特定的发现（如"这个命主的火库怎么开"）→ 写入命主级文档，不上升到本方法论
- 流派偏好变化（如想从子平派切到滴天髓派）→ 重大决定，应整体讨论

### 6.3 当前已识别的待办

- [ ] 多排盘软件适配：当前仅基于《南方排八字专业程序》的输出格式做了过滤；未来如果引入其他软件（如《中华万年历》排盘、专业版易奇八字、紫薇斗数同类），需检查其输出是否有新的黑箱类别
- [ ] schema 校验：未来 `bazi-static-analysis_{1,2,3}.json` 可定义 JSON Schema，CI 跑校验
- [ ] 自动化 prompt：把本流程包装成 prompt 后，可以在新命主接入时一键生成静态分析骨架
